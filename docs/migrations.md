# データベースマイグレーション

スキーマは **Flyway** が管理する。Hibernate はスキーマを変更せず、検証するだけ
(`spring.jpa.hibernate.ddl-auto=validate`)。エンティティとスキーマがずれていれば
アプリケーションは起動に失敗する。

以前は `ddl-auto=update` で Hibernate にスキーマを作らせていた。この方式には
次の問題がある。

- カラムの削除・リネーム・型変更が行われない (ドリフトが静かに蓄積する)
- 適用されたスキーマがコードから追跡できず、環境ごとに差異が生じる
- データを伴う変更 (NOT NULL 化の前のバックフィルなど) を表現できない
- 本番と同じ手順を開発・CI で再現できない

## 1. ファイルの配置

```
src/main/resources/db/migration/
├── V1__baseline_schema.sql                   # Flyway 導入前のスキーマ
└── V2__file_size_content_type_and_indexes.sql
```

命名は `V<バージョン>__<説明>.sql`。バージョンは連番、説明はスネークケース。

## 2. マイグレーションを追加する

1. `V<次の番号>__<変更内容>.sql` を作成する
2. エンティティを対応する形に変更する
3. `mvn test` を実行する。`SchemaMigrationTest` がマイグレーション自体を検証し、
   他のテストは `ddl-auto=validate` の下で動くため、エンティティとの不一致は
   起動時に検出される

### 適用済みのファイルは編集しない

Flyway は適用時にチェックサムを記録する。既に適用されたファイルを編集すると、
そのデータベースでは次回起動時に検証エラーになる。訂正は必ず新しい
マイグレーションで行う。

### 稼働中のデータを壊さない書き方

本番のテーブルには既にデータが入っている前提で書く。

```sql
-- NOT NULL を付ける前に、既存行へ値を入れる
ALTER TABLE files ADD COLUMN example BOOLEAN;
UPDATE files SET example = FALSE WHERE example IS NULL;
ALTER TABLE files ALTER COLUMN example SET NOT NULL;
```

- カラムの追加は NULL 許容で追加し、バックフィル後に制約を付ける
- 大きなテーブルへのインデックス作成はロック時間に注意する
  (PostgreSQL では `CREATE INDEX CONCURRENTLY` を検討する。ただし Flyway では
  トランザクション外で実行する設定が必要)
- 破壊的な変更 (カラム削除・リネーム) は、アプリケーションが新旧どちらの
  スキーマでも動く状態を経由して 2 回に分ける

## 3. SQL の可搬性

本番は PostgreSQL、開発とテストは H2 を使う。**マイグレーションは 1 系統**で、
両方で動く SQL だけを書く。

| 用途 | 使う構文 | 使わない構文 |
| :--- | :--- | :--- |
| 自動採番 | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `BIGSERIAL`, `AUTO_INCREMENT` |
| 日時 | `TIMESTAMP(6)` | `TIMESTAMPTZ` |
| 型変更 | `ALTER COLUMN c SET DATA TYPE t` | `ALTER COLUMN c TYPE t` (H2 で不可) |

ベンダー固有の SQL が必要になった場合は `spring.flyway.locations` に
`classpath:db/migration/{vendor}` を使って分割できるが、分割した時点で
それぞれのファイルは片方の DB でしか実行されなくなる。可搬な SQL で書ける
うちは 1 系統に保つ方が安全。

CI には PostgreSQL に対してマイグレーションを適用するジョブがある
(`.github/workflows/ci.yml` の `postgres-migrations`)。H2 でしか試していない
SQL がマージされることはない。

## 4. Flyway 導入前のデータベースを移行する

`spring.flyway.baseline-on-migrate=true` と `baseline-version=1` により、
起動時に自動で処理される。

| データベースの状態 | Flyway の動作 |
| :--- | :--- |
| 空 | ベースラインを作らず V1 から全て適用 |
| 既存 (Flyway 管理外) | V1 として記録し、V2 以降を適用 |
| 既存 (Flyway 管理下) | 未適用のものだけ適用 |

`V1__baseline_schema.sql` は **Flyway 導入前のスキーマそのまま**であり、
既存データベースの状態と一致する。だからこそ V1 として記録して差し支えない。
V1 を「あるべき最新のスキーマ」に書き換えてはいけない。既存データベースは
その変更を受け取れなくなる。

この移行経路は `SchemaMigrationTest#aDatabaseThatPredatesFlywayIsBaselinedAndUpgraded`
で検証している。

## 5. 状態の確認

```sql
SELECT version, description, type, success, installed_on
FROM flyway_schema_history ORDER BY installed_rank;
```

| type | 意味 |
| :--- | :--- |
| `SQL` | マイグレーションファイルが適用された |
| `BASELINE` | Flyway 導入前から存在していたスキーマとして記録された |

`success = false` の行がある場合、そのマイグレーションは途中で失敗している。
原因を取り除いたうえで `flyway repair` を実行し、再度起動する。

## 6. ロールバック

Flyway Community Edition に `undo` はない。切り戻しが必要な場合は、打ち消す
内容の新しいマイグレーションを追加する。デプロイ前のバックアップ取得は
[operations.md](./operations.md) を参照。
